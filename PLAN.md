# PLAN.md — Habit tracker v1

Офлайн-трекер привычек. Без бэкенда, аккаунтов и сети. **v1 — только iOS.**

**Статус: этапы 1–12 выполнены, этап 13 запланирован.**
Документ живой: разделы 1–4 описывают то, что лежит в коде, а не то, что планировалось;
ещё не сделанные этапы несут собственные блоки схемы и файлов
и переезжают в общие разделы, когда написаны.
Следующая работа — новым этапом ниже, с новым блоком миграции, если она трогает схему.

## Базовые решения

**Данные и расчёты**

- Стрик считается только по запланированным дням; дни вне расписания его не ломают.
- Незакрытый сегодняшний день стрик не обнуляет: стрик считается до последнего
  прошедшего запланированного дня, сегодня добавляет +1 только когда закрыт.
- День закрыт только при 100% цели; хитмап красит клетку по доле выполнения
  (`count / target_per_day`, зажатой в 0..1).
- Проценты за 7 и 30 дней считаются **от запланированных дней** в окне, не от
  календарных. Иначе привычка на 3 дня в неделю никогда не поднимется выше 43%,
  что противоречило бы правилу стрика.
- Расписание и цель **не версионируются**: статистика всегда считается текущими
  настройками привычки. Правка расписания или цели задним числом меняет прошлые
  стрики и хитмап — это принято осознанно, ради простой схемы. Если нужна честная
  история — заводится новая привычка.
- Дата — всегда строка `YYYY-MM-DD` в локальной таймзоне.
- Стрики и статистика считаются из `entries`, не хранятся отдельно.
- **Привычка не существует до дня своего создания.** `created_at` задаёт начало её
  истории: более ранние дни не считаются пропущенными, иначе каждая новая привычка
  открывалась бы нулевым стриком и 0% за 30 дней. Начало отодвигается назад, если
  есть запись старше — отмеченный задним числом день или импортированная история.
  То же правило работает на «Сегодня»: при листании назад привычка не показывается в
  днях до своего появления, кроме тех, где у неё уже есть отметка.

**Взаимодействие**

- Прошлые дни правятся через переключатель даты на экране «Сегодня».
- Полоска дат листается по неделям стрелками. Назад — без ограничения (это и есть
  доступ к истории), вперёд — до недели с сегодняшним днём: дальше отмечать нечего,
  а неограниченная прокрутка вперёд уводит в месяц, из которого потом надо
  выщёлкиваться назад. Над полоской — название месяца (или двух, если неделя их
  разделяет), иначе после перелистывания семь голых чисел не говорят, какая это
  неделя. Год в подписи появляется, только когда неделя не в текущем году.
- Перелистывание сохраняет выбранный день недели: шаг назад с четверга даёт четверг
  предыдущей недели. Шаг вперёд, попавший за сегодня, зажимается на сегодня.
- Будущие дни в полоске видны (бледные, видно что запланировано), но отмечать в них
  нельзя.
- Тап по кнопке отметки крутит счётчик по циклу `0 → 1 → … → N → 0`.
- Long-press по карточке — контекстное меню «Изменить / Архивировать».

**Платформа и оформление**

- v1 — iOS-only. Android не тестируем и намеренно не поддерживаем: каналы
  уведомлений, `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM` и PNG-фолбэки иконок в
  скоуп не входят. Веб выпиливается из проекта на этапе 1.
- Тема — «Системная / Светлая / Тёмная», переключатель в настройках; значение лежит
  в `app_settings` под ключом `theme_mode`, по умолчанию системная. Читается одним
  `load()` вместе с языком до снятия splash — иначе выбранная тема моргала бы
  системной на первом кадре.
- Два языка UI: русский и английский, переключаются в настройках; по умолчанию —
  русский, режима «системный» нет (этап 11). Пользовательские данные — названия
  привычек — не переводятся.
- Шрифт не масштабируется системным Dynamic Type: `allowFontScaling: false` в
  базовом `components/ui/text.tsx`.
- Иконки — SF Symbols через `expo-symbols`.

## 2. Схема БД

SQLite через `expo-sqlite`. Открытие —
`<SQLiteProvider databaseName="habits.db" onInit={migrate} useSuspense>` внутри
`<Suspense>` в корневом `_layout.tsx`.

**Прагмы.** `PRAGMA foreign_keys = ON` — прагма уровня *соединения*, а не файла: она
выполняется **в начале `migrate(db)`, до проверки `user_version`**, то есть при
каждом открытии базы, и в любом другом соединении, если такое появится. Если
спрятать её внутрь блока миграции v0→v1, со второго запуска приложения
`ON DELETE CASCADE` тихо перестанет работать. `PRAGMA journal_mode = WAL` наоборот
персистентна — её достаточно выполнить один раз при создании базы.

### `habits`

| Поле | Тип | Описание |
|---|---|---|
| `id` | TEXT PK | uuid v4 из `expo-crypto` (стабилен при экспорте/импорте) |
| `name` | TEXT NOT NULL | название |
| `emoji` | TEXT NOT NULL | одна эмодзи из фиксированного набора |
| `color_key` | TEXT NOT NULL | **ключ** из палитры (`violet`, `teal`, …), не hex |
| `target_per_day` | INTEGER NOT NULL DEFAULT 1 | `CHECK (target_per_day >= 1)` |
| `schedule_mask` | INTEGER NOT NULL DEFAULT 127 | битовая маска дней, бит 0 = понедельник … бит 6 = воскресенье; `CHECK (schedule_mask > 0 AND schedule_mask <= 127)` |
| `reminder_time` | TEXT NULL | `'HH:mm'` локального времени, NULL = без напоминания |
| `sort_order` | INTEGER NOT NULL | порядок в списке; при создании = `max+1` |
| `archived_at` | TEXT NULL | ISO-таймстемп архивации; NULL = активна |
| `created_at` / `updated_at` | TEXT NOT NULL | ISO-таймстемпы |

Индекс: `CREATE INDEX idx_habits_active ON habits(archived_at, sort_order)`.

**Почему `color_key`, а не hex:** цвет привычки обязан меняться вместе с темой.
Храня hex, мы бы зафиксировали светлый вариант навсегда и нарушили правило
«цвета только из токенов».

**Почему маска, а не таблица дней:** 7 бит вместо 7 строк на привычку, проверка
«сегодня запланировано» — одна побитовая операция, никаких JOIN на горячем пути
экрана «Сегодня».

**Почему `CHECK (schedule_mask > 0)`:** привычка с пустым расписанием не появлялась
бы ни на одном экране и стала бы невидимым призраком. Форма создания это же
проверяет и не даёт снять последний день.

### `entries`

| Поле | Тип | Описание |
|---|---|---|
| `habit_id` | TEXT NOT NULL | `REFERENCES habits(id) ON DELETE CASCADE` |
| `date` | TEXT NOT NULL | `'YYYY-MM-DD'` в локальной таймзоне |
| `count` | INTEGER NOT NULL | `CHECK (count > 0)`; строка удаляется при обнулении |
| `updated_at` | TEXT NOT NULL | ISO |

`PRIMARY KEY (habit_id, date)` — он же покрывающий индекс для «все дни одной
привычки». Дополнительно: `CREATE INDEX idx_entries_date ON entries(date)` — для
«прогресс конкретного дня по всем привычкам» (экран «Сегодня»).

**Почему одна строка на день, а не строка на тап:** все запросы приложения
агрегатные (сколько за день, закрыт ли день). `count` убирает `GROUP BY` с каждого
рендера и держит таблицу маленькой — 365 строк на привычку в год. Цена: не храним
время каждого нажатия, но в скоуп v1 это не входит.

**`count` против уменьшенной цели.** После правки `target_per_day` с 3 на 1 старые
записи с `count = 3` дают долю 300%. Во всех расчётах доля зажимается:
`min(count / target_per_day, 1)`. Запись при этом не трогаем.

**Записи на днях вне расписания.** После снятия дня недели старые записи на нём
остаются. Правило: в хитмапе такая клетка красится по доле выполнения как обычно
(данные есть — показываем), но в стрике и процентах участвуют только запланированные
дни.

### `expense_categories`

| Поле | Тип | Описание |
|---|---|---|
| `id` | TEXT PK | uuid v4 |
| `name` | TEXT NOT NULL | название |
| `emoji` | TEXT NOT NULL | одна эмодзи из набора `constants/emoji.ts` |
| `color_key` | TEXT NOT NULL | ключ из **палитры трат** (16 цветов), не hex |
| `sort_order` | INTEGER NOT NULL | порядок в сетке; при создании = `max+1` |
| `archived_at` | TEXT NULL | ISO-таймстемп архивации; NULL = активна |
| `created_at` / `updated_at` | TEXT NOT NULL | ISO |

Индекс: `CREATE INDEX idx_expense_categories_active ON expense_categories(archived_at, sort_order)`.

**Восемь категорий засеяны самой миграцией** одним проходом: Здоровье, Досуг, Дом, Еда,
Развлечение, Покупки, Транспорт, Прочее — каждая со своим цветом и эмодзи. Не при первом
рендере: иначе понадобился бы флаг «сидинг выполнен» в `app_settings` и ветка на каждом
старте. Миграция выполняется ровно один раз, поэтому пользователь, заархивировавший все
восемь, не получит их обратно — так и задумано. Названия сидируются по-русски и **не
переводятся при смене языка**: это те же пользовательские данные, что и названия привычек.

### `expenses`

| Поле | Тип | Описание |
|---|---|---|
| `id` | TEXT PK | uuid v4 |
| `category_id` | TEXT NOT NULL | `REFERENCES expense_categories(id) ON DELETE RESTRICT` |
| `amount` | INTEGER NOT NULL | целые единицы, `CHECK (amount > 0)` |
| `date` | TEXT NOT NULL | `'YYYY-MM-DD'` в локальной таймзоне |
| `created_at` / `updated_at` | TEXT NOT NULL | ISO |

Индексы: `CREATE INDEX idx_expenses_date ON expenses(date)` — период и день читаются
диапазоном по датам; `CREATE INDEX idx_expenses_category ON expenses(category_id)` —
проверка «категория пуста» перед удалением.

**Почему у траты собственный `id`, а не составной ключ, как у `entries`.** В `entries`
одна строка на день по построению — там счётчик. Трат в один день по одной категории
может быть сколько угодно, и каждая правится и удаляется отдельно; составной ключ
превратил бы вторую «Еду» за день в перезапись первой.

**Почему `ON DELETE RESTRICT`, а не `CASCADE`, как у привычек.** Удаление привычки
осмысленно уносит её отметки: без привычки они ничего не значат. Траты — деньги,
которые уже ушли: удаление категории не должно менять сумму прошлого месяца. Правило
«категория с тратами не удаляется, а архивируется» держится схемой, а не только
проверкой в UI. Полное удаление доступно только для категории без трат.

### `expense_budgets`

| Поле | Тип | Описание |
|---|---|---|
| `period_start` | TEXT PK | `'YYYY-MM-DD'` — первый день периода |
| `amount` | INTEGER NOT NULL | `CHECK (amount > 0)` |
| `updated_at` | TEXT NOT NULL | ISO |

Строка заводится только на тот период, которому бюджет задали явно. Период без своей
строки наследует последнюю строку **до** своего начала — правило живёт в
`lib/expenses.ts` (`resolveBudget`), см. этап 12.1.

### `app_settings`

`key TEXT PRIMARY KEY, value TEXT NOT NULL` — плоские настройки. Сейчас в ней живут
`theme_mode` (этап 10), `language` (этап 11) и `expense_period_start_day` (этап 12.1) —
день начала периода трат, `'1'`..`'28'`, дефолт `'1'`. **В v1 таблица
создаётся, но остаётся пустой:** флага онбординга нет (экрана онбординга в v1 нет),
времени последнего пересчёта уведомлений нет (при стратегии полного пересчёта он
никем не читается), версия формата экспорта живёт в самом файле экспорта. Таблица
существует затем, чтобы первая же будущая настройка не потребовала миграции схемы.

### Что НЕ храним

Стрики, «лучший стрик», проценты за 7/30 дней, суммы за день — всё считается на
лету из `entries`. Причина: любая правка задним числом мгновенно делает кэш
неверным, а объём данных микроскопический (одна привычка за 3 года ≈ 1000 строк —
читается за миллисекунды). Уведомления тоже не храним: их id восстанавливаются
полным пересчётом.

### Миграции

`PRAGMA user_version` + последовательные блоки в `migrate(db)`, как в официальном
примере expo-sqlite:

```ts
const DATABASE_VERSION = 2;
// PRAGMA foreign_keys = ON — здесь, ДО проверки версии
// v0 -> v1: WAL, создание habits, entries, app_settings, индексов
// v1 -> v2: expense_categories, expenses, expense_budgets, индексы, сидинг 8 категорий
// v2 -> v3: следующая миграция добавляется НОВЫМ блоком, старые не редактируются
```

Правило на весь проект: изменение уже выпущенной миграции запрещено — только новый
блок с инкрементом `DATABASE_VERSION`.

### Этап 3 — Экран «Сегодня»

Файлы: `(tabs)/index.tsx`, `components/habit/habit-card.tsx`, `check-button.tsx`,
`progress-bar.tsx`, `day-strip.tsx`, `store/entries-store.ts`, плюс `lib/date.ts`
(`weekDates`, `weekStartKey`, `shiftDateKey` — арифметика недели для полоски).

Стор — источник истины для UI, база — для хранения. Стор `entries` кеширует видимый
диапазон дат и перезагружается при перелистывании недели. Отметка идёт через
действие стора `cycle(db, habitId, date, target)`: оно берёт текущее значение из
стора, патчит ячейку синхронно и только потом ждёт запись в репозиторий, откатывая
ячейку при ошибке. Считать следующее значение в компоненте нельзя — два тапа внутри
одной незавершённой записи прочитают одно и то же значение, и второй тап потеряется.

**Готово, когда:** вижу полоску дат недели и список привычек, запланированных на
выбранный день (FlatList); тап по кнопке с целью 1 закрывает привычку, повторный —
снимает; с целью N счётчик идёт `1/3 → 2/3 → 3/3 → 0/3`, и быстрая серия тапов не
теряет ни одного (следующее значение берётся из стора, а не из замыкания рендера);
полоса сверху показывает процент дня; тап по вчерашней дате даёт править вчерашний
день; стрелки листают полоску по неделям — назад сколько угодно, вперёд до текущей
недели, и подпись над полоской называет месяц; будущие даты видны бледными и кнопки
отметки в них неактивны; long-press по карточке открывает меню «Изменить /
Архивировать» («Изменить» ведёт в модалку `habit/[id]`); приложение, оставленное
открытым через полночь, само переезжает на новый день (`AppState` + таймер до
ближайшей полуночи) — при этом полоска, показывавшая текущую неделю, переезжает
вместе с ним, а неделя, на которую пользователь ушёл сам, остаётся; закрытие и
открытие приложения сохраняет отметки.

Коммит: `feat: today screen with day strip and completion`.

### Этап 4 — Создание и редактирование привычки

Файлы: `app/habit/new.tsx`, `app/habit/[id].tsx`, `components/habit/habit-form.tsx`,
`color-picker.tsx`, `emoji-picker.tsx`, `weekday-picker.tsx`, `time-picker-field.tsx`,
`constants/emoji.ts`.

Оба роута — тонкие обёртки над одной `HabitForm`: различаются начальными значениями,
подписью кнопки и действием стора (`create` / `update`). Форма держит значения в
локальном состоянии и отдаёт наружу готовый `HabitInput`; куда его писать, решает
роут.

Время напоминания — `DatePicker` из `@expo/ui` (новых зависимостей не требуется).
Эмодзи — сетка из фиксированного набора в `constants/emoji.ts` (40 штук), свободного
ввода нет, поэтому валидация «ровно одна эмодзи» не нужна. Цель в день — степпер
1..20: верхняя граница нужна только чтобы «+» не уводил счётчик в бессмысленные
числа, схема о ней не знает.

Правила формы: сохранение блокируется, пока пустое название или снят последний день
недели, и каждый случай подписан строкой под своим блоком. Ключ цвета нормализуется
при открытии — иначе привычка с чужим ключом открылась бы без выбранного свотча и
вернула бы его в базу. Ошибка записи ловится в форме и показывается `Alert`: иначе
она уходит в unhandled rejection, а экран остаётся открытым, будто всё сохранилось.
Выключение напоминания стирает время, но форма помнит последнее выбранное и
возвращает его при обратном включении; включение с нуля даёт `09:00`, а не текущую
минуту.

Экран `habit/[id]` берёт привычку из стора и, если тот ещё не загружен, грузит его
сам: без этого прямой заход (диплинк, тап по уведомлению на этапе 7) показал бы
«Привычка не найдена» вместо формы. Пустое состояние показывается только после
загрузки списка.

**Готово, когда:** кнопка «+» открывает модалку; задаю название, эмодзи из сетки,
цвет из 8, дни недели, цель 1..N, время напоминания (поле сохраняется, но пока
ничего не шлёт); снять последний день недели или оставить пустое название нельзя —
кнопка сохранения блокируется, и под соответствующим блоком видно, почему; выбранные
эмодзи и цвет читаются как выбранные в обеих темах, а любой свотч и любая клетка
ловят тап на 44pt; клавиатура не закрывает кнопку сохранения; после сохранения
привычка появляется на «Сегодня» с выбранным цветом как акцентом карточки;
редактирование существующей меняет её, снятие дня недели убирает её из
соответствующих дней.

Коммит: `feat: habit create and edit form`.

### Этап 5 — Анимации и haptics

Ставим: `expo-haptics`.

Файлы: `components/ui/pressable-scale.tsx`, `check-button.tsx`, `progress-bar.tsx`,
`lib/haptics.ts`, `(tabs)/index.tsx`.

`lib/haptics.ts` даёт три намерения, а не сырые стили отклика: `tick` (шаг вперёд),
`reset` (обнуление счётчика, глуше `tick`) и `success` (день закрыт целиком). Промис
`expo-haptics` внутри обёртки гасится: на устройстве без Taptic Engine он отклоняется,
и незаловленное отклонение всплыло бы warning'ом в Metro из-за отклика, которого
пользователь всё равно не должен заметить.

**Отклик выбирает экран, а не кнопка.** Тап, закрывающий день, повышает `tick` до
`success`; если бы кнопка отметки тоже стучала, на одном тапе проигрывались бы два
накладывающихся паттерна. Поэтому `check-button.tsx` отвечает только за пружинный
отскок (сжатие при обнулении, перелёт на остальных шагах), а решение принимает
`handleToggle` на «Сегодня» — единственное место, где известны и счётчик, и итог дня.

**Оба значения читаются из стора, а не из пропсов рендера.** `cycle` патчит свою
ячейку синхронно и только потом ждёт запись, так что состояние сразу после вызова —
уже послетаповое. Пропсы внутри быстрой серии тапов ещё показывают дотаповый счётчик
и назвали бы возврат к нулю шагом вперёд. Сравнивать `dayProgress` между рендерами
тоже нельзя: записи приезжают после первого рендера, и уже закрытый день поздравлял
бы с закрытием при каждом открытии приложения и при каждом перелистывании на него.

Все анимации получают `ReduceMotion.System` — с включённым «Уменьшением движения» в
iOS они не проигрываются, а мгновенно встают в конечное значение. Полоса дня
доезжает `withTiming` на `motion.timing.base` с ease-out (то самое задокументированное
исключение из правила «только transform / opacity», см. раздел 4).

Отдельного pressed-сжатия у карточки нет и не будет: её единственный жест —
long-press, а его отрабатывает нативный SwiftUI `ContextMenu` внутри `MenuView` со
своим подъёмом карточки. JS-скейл поверх дублировал бы нативную анимацию и рисковал
залипнуть сжатым, не получив press-out после перехвата жеста. Pressed-сжатие несут
все обычные интерактивы через `PressableScale`.

**Готово, когда:** любое нажимаемое (кнопки, свотчи, клетки дней, дни недели, эмодзи)
даёт pressed-сжатие, а long-press по карточке — нативный подъём с меню; отметка —
пружинный отскок галочки и лёгкий haptic, полоса дня доезжает плавно; при 100% дня —
более заметный success-haptic **вместо** лёгкого, ровно один на тап; обнуление
счётчика даёт отдельный, более глухой отклик; открытие приложения на уже закрытом дне
и перелистывание на такой день молчат; прокрутка списка на устройстве без рывков.

Коммит: `feat: check animation and haptics`.

### Этап 6 — Статистика

Ставить нечего: `jest`, `jest-expo` и `@types/jest` пришли с шаблоном и уже стоят
(`npm test` = `jest --passWithNoTests`).

Файлы: `lib/streaks.ts`, `lib/__tests__/*`, `(tabs)/stats.tsx`,
`components/stats/heatmap.tsx`, `streak-card.tsx`, `rate-card.tsx`,
`hooks/use-today-key.ts` (выносится из `(tabs)/index.tsx`), `tsconfig.json`.

Тесты покрывают только чистую логику — `date.ts`, `schedule.ts`, `streaks.ts`.
Компоненты и репозитории не тестируем. `tsconfig.json` получает `"types": ["jest"]`,
иначе `describe` / `it` не типизированы.

Экран берёт привычки **напрямую из репозитория, а не из `habits-store`**: у стора
область `includeArchived` глобальная, и переключатель «Архивные» здесь молча
расширил бы её и для «Сегодня». Цена — свой стейт и своя перезагрузка.

**Перезагрузка по фокусу.** Табы остаются смонтированными, поэтому экран, загрузивший
данные один раз при монтировании, показывал бы стрик и хитмап без отметок, сделанных
на «Сегодня» после этого. Оба запроса перевыполняются на каждый `useIsFocused()`.

**Записи читаются все разом, а не по привычке.** Один `listAllEntries` на фокус вместо
запроса на каждое переключение чипа: обзор «Все привычки» всё равно требует всей
таблицы, а переключение между привычками после загрузки становится чистой деривацией —
ждать нечего и мигнуть историей предыдущей привычки нечем. Гонки медленных запросов,
из-за которой историю приходилось держать вместе с id её привычки, при таком чтении
просто нет. Цена — одна выборка `entries` целиком: строка на привычку на отмеченный
день, несколько тысяч строк за годы использования.

**Обзор «Все привычки».** Первый чип в селекторе — не привычка, а агрегат по всем
показанным (id `'all'`, с uuid не столкнётся). Ради него вся статистика считается над
**списком** серий (`HabitSeries[]`): одна выбранная привычка — это список из одного
элемента, идущий тем же кодом. День засчитывается в стрик, когда закрыты **все**
запланированные на него привычки, а проценты берут знаменателем каждый запланированный
день каждой привычки, поэтому день, где сделали два дела из трёх, читается как 2/3, а
не как полный промах.

Ключ «сегодня» — общий хук `hooks/use-today-key.ts`, поднятый сюда из «Сегодня»
(этап 3). Захваченный один раз при монтировании, он после полуночи обрезал бы стрик и
хитмап по вчерашнему дню.

Ячейка хитмапа — цвет привычки с альфой по доле выполнения (`0` — едва заметный тон,
чтобы запланированный несделанный день читался как клетка, а не как пустота). Будущие
дни и дни до появления привычки не красятся вовсе: иначе остаток текущего месяца
выглядел бы стеной провалов.

**Хитмап — три месячные сетки рядом, а не скользящая лента недель.** Каждый месяц
рисуется настоящим календарём: колонка = день недели (понедельник первый, как и
`schedule_mask`), месяц, начинающийся со среды, открывается двумя пустыми слотами.
Лента из 13 недель выстраивала клетки подряд и не давала показать пальцем на дату —
ровно то, ради чего хитмап и нужен. Подпись месяца стоит над своей сеткой, поэтому
никакого абсолютного позиционирования ей больше не требуется.

**Готово, когда:** на экране статистики выбираю привычку (включая архивные —
у селектора есть переключатель «показывать архивные») или обзор «Все привычки» и вижу
текущий и лучший стрик, проценты за 7 и 30 дней, хитмап за 3 месяца — три месячные
сетки рядом; клетка частично выполненного дня
бледнее полностью закрытой, день вне расписания без записи красится токеном
`unscheduled`; дни вне расписания не ломают стрик (проверяю на привычке пн/ср/пт:
закрыл пн и ср, вторник пропустил — стрик 2); незакрытый сегодняшний день стрик не
обнуляет; `npx jest` зелёный, в тестах есть кейсы на границу месяца (в том числе
`shiftDateKey` на ±7 дней через 1-е число), на переход через воскресенье
(`weekStartKey` даёт понедельник и для самого воскресенья) и на конверсию нумерации
дней недели; отметка на «Сегодня» видна в стриках и хитмапе сразу после возврата на
вкладку статистики; переключение привычки не показывает историю предыдущей.

Коммит: `feat: stats screen with streaks and heatmap`.

### Этап 7 — Локальные уведомления

Ставим: `expo-notifications`.

Файлы: `lib/notifications.ts`, `app/_layout.tsx`, `store/habits-store.ts`,
`components/habit/time-picker-field.tsx`, `(tabs)/settings.tsx`.

Обязательный минимум, помимо планирования:
- `setNotificationHandler` — иначе уведомление при открытом приложении не покажется;
- `getLastNotificationResponse()` рядом с `addNotificationResponseReceivedListener` —
  листенер не ловит запуск приложения из убитого состояния. Обработанный ответ гасится
  `clearLastNotificationResponse()`: он переживает перезапуск, и без этого один тап по
  уведомлению уводил бы на «Сегодня» при каждом следующем холодном старте;
- полный пересчёт (`cancelAllScheduledNotificationsAsync` → планирование заново)
  защищён простым мьютексом в `lib/notifications.ts`: два быстрых сохранения подряд
  или сохранение во время импорта не должны накладываться. Вызывается из
  `habits-store` после любой мутации (create / update / archive / unarchive / delete);
- триггеры: все 7 дней — один `DAILY`, иначе по одному `CALENDAR` с `weekday` и
  `repeats: true` на каждый день (см. лимит iOS в разделе 6);
- разрешение запрашивается только из мутации стора (`requestPermission: true`) — то
  есть на сохранении привычки. Фоновый пересчёт системный диалог не показывает
  никогда;
- без разрешения планирование пропускается целиком: iOS отклоняет каждый запрос без
  авторизации, и попытка дала бы только поток ошибок в лог;
- `useReminderSync(db)` в корневом `_layout.tsx` — пересчёт при запуске и на возврате
  в `active`, когда статус **только что стал** `granted`. Без него разрешение, выданное
  задним числом в настройках iOS, оставалось бы без расписания до следующей правки
  привычки: всё, что планировалось при запрете, было отклонено системой;
- отказ в разрешении: время в привычке сохраняется, но в форме (под переключателем
  напоминания в `time-picker-field.tsx`) и в настройках висит предупреждение с кнопкой
  в системные настройки (`Linking.openSettings`); статус перепроверяется при каждом
  возврате приложения в `active`. На iOS смотрим `ios.status`, а не корневой `status`.

**Готово, когда:** при первом сохранении привычки с временем запрашивается
разрешение; уведомление приходит в заданное время только в запланированный день и
показывается в том числе при открытом приложении; смена времени или дней меняет
расписание (проверяю через `getAllScheduledNotificationsAsync()` в логе); архивация
или удаление привычки снимает её уведомления; тап по уведомлению открывает
«Сегодня» и из фона, и с холодного старта, а следующий обычный запуск никуда не
перекидывает; отказ в разрешении даёт баннер с переходом в настройки, а не молчание,
и разрешение, выданное после отказа в настройках iOS, само поднимает расписание при
возврате в приложение.

Коммит: `feat: local reminders`.

### Этап 8 — Архив, удаление, порядок, настройки

Файлы: `(tabs)/settings.tsx`, `app/habit/[id].tsx`, `db/habits-repo.ts`,
`store/habits-store.ts`, `(tabs)/index.tsx`.

**Область стора.** Экран настроек — единственное место, где нужен полный список, и
именно он грузит стор с `includeArchived: true`. Область глобальная и переживает
write-through (`reload` сохраняет её сам), из чего следуют два хвоста:

- «Сегодня» отфильтровывает архивные сам (`activeHabits`), иначе после захода в
  настройки архивная привычка вернулась бы в список дня и в полосу прогресса;
- `habit/[id]`, не найдя привычку в сторе, догружает список **с архивными**. Это и
  чинит «Привычка не найдена» при прямом заходе (диплинк, тап по уведомлению) на
  архивную: догружать в той же узкой области значило бы повторить запрос, который уже
  промахнулся. Догрузка одноразовая — несуществующий id должен осесть на пустом
  состоянии, а не перезапрашивать список каждый рендер, — и пустое состояние
  показывается только после неё.

**Порядок — стрелки, не перетаскивание:** DnD в `FlatList` требует внешней
зависимости, а список привычек короткий. `reorderHabits` переписывает `sort_order`
пачкой в одной транзакции и только для переданных id: архивные, лежащие между
активными, сохраняют своё значение, а их взаимный порядок нигде не показывается.
Действие стора `reorder` сначала переставляет список в сторе и только потом ждёт
запись — по той же причине, что и `cycle` на «Сегодня»: второй тап по стрелке внутри
незавершённой записи иначе считал бы перестановку от дотапового порядка и повторил
первую, потеряв ход. Сортировка стабильная, поэтому привычки вне переданного списка
держат своё относительное место; при ошибке записи список откатывается.

**Строка списка — обычный `View`, а не одно большое нажимаемое.** Стрелки и меню —
нажимаемые сами по себе, и внутри общего `Pressable` выключенная стрелка отдавала бы
тап наружу (открывался бы экран редактирования), а нативный триггер меню спорил бы за
тот же тап. Форму открывает только область с эмодзи и названием.

**Мутации идут через общий `runMutation`.** Он гасит отказ (иначе — unhandled
rejection в Metro на ошибке, которую пользователь всё равно только повторит) и
перечитывает счётчик запланированных уведомлений: архивация, разархивация и удаление
пересчитывают расписание, а баннер о лимите iOS иначе показывал бы домутационное
число до следующего входа на вкладку.

Удаление подтверждается `Alert`; записи уносит `ON DELETE CASCADE`, отдельного
запроса по `entries` нет.

**Готово, когда:** в настройках вижу список привычек, могу менять их порядок
стрелками (`sort_order` переписывается пачкой в транзакции, новый порядок виден на
«Сегодня», и быстрая серия тапов по стрелке не теряет ни одного хода), могу
архивировать (уходит с «Сегодня», история остаётся видна в статистике) и
разархивировать (привычка встаёт в конец списка); удаление спрашивает подтверждение и
сносит привычку вместе с записями (каскад); тап по названию архивной привычки
открывает её форму, а не «Привычка не найдена»; выключенная стрелка у крайней
привычки ничего не открывает.

Коммит: `feat: archive, reorder, delete and settings`.

### Этап 9 — Экспорт и импорт JSON

Ставим: `expo-file-system`, `expo-sharing`, `expo-document-picker`. В `plugins`
`app.json` ничего не добавляется: конфиг-плагин `expo-sharing` — это share extension
(приём файлов **в** приложение), без пропсов он no-op, а `Sharing.shareAsync` плагина
не требует вовсе. Строка `"expo-sharing"` в плагинах только вводила бы в заблуждение.

Файлы: `lib/backup.ts`, `(tabs)/settings.tsx`, `store/entries-store.ts`.

**Формат.** Файл несёт собственное поле `version`, и импорт по нему решает, умеет ли
он это читать: версия больше `BACKUP_VERSION` отклоняется с внятным текстом, а не
читается «как v1». Иначе бэкап от будущей сборки, знающей о колонках и правилах,
которых здесь нет, молча потерял бы их часть. Валидация структуры — руками, без новых
зависимостей; неизвестный `color_key` откатывается на `violet` через тот же
`resolveColorKey`, что и форма.

**Порядок проверок: сначала версия, потом структура.** Файл будущей версии и должен не
пройти построчную проверку v1 — у него другие колонки. Проверь структуру первой, и
единственный случай, ради которого поле `version` вообще существует, отвечал бы
«формат не распознан».

**Проверяются значения, а не только типы.** Тип строки ничего не гарантирует, а всё
внутри файла — недоверенный ввод: `2026-02-31` проходит проверку на форму `YYYY-MM-DD`,
но парсится в Invalid Date, и первый же `shiftDateKey` роняет расчёт стрика прямо из
рендера «Статистики»; `reminder_time: "вечером"` превращается в NaN-час и обрывает
пересчёт расписания для всех привычек, идущих следом. В схеме CHECK ни на то, ни на
другое нет, так что импорт — единственное место, где это можно отклонить:
`isValidDateKey` и `isValidTimeOfDay` в `lib/date.ts`.

**Импорт — полная замена**, внутри одной `withExclusiveTransactionAsync` с откатом при
любой ошибке (обычный `withTransactionAsync` захватывает и посторонние параллельные
запросы — задокументированная ловушка expo-sqlite).

**Транзакция идёт по своему соединению.** `withExclusiveTransactionAsync` открывает
подключение с `useNewConnection: true`, а `PRAGMA foreign_keys` — прагма уровня
соединения и выполняется только в `migrate()` на основном (см. раздел 2). Значит
внутри транзакции каскада и внешних ключей нет: `entries` удаляются явно и до
`habits`, а принадлежность каждой записи существующей привычке проверяется в JS
**до** первой записи, а не доверяется ограничению, которое здесь не действует.

**После импорта оба стора перезагружаются вручную.** Импорт пишет прямо в SQL, минуя
мутации репозитория, которые оборачивают действия сторов, — поэтому ни write-through
перезагрузки, ни пересчёта уведомлений не случается само. `habits-store` грузится
заново с архивными (область экрана настроек), `entries-store` перечитывает видимый
диапазон своим `reload`: вкладка «Сегодня» остаётся смонтированной, её эффект завязан
на смену недели и не сработал бы — экран показывал бы отметки только что стёртых
данных. Затем — полный пересчёт расписания и перечитывание счётчика уведомлений для
баннера о лимите iOS.

**Экспорт** пишет файл с датой в имени и `overwrite: true`, а не с таймстемпом: имя
видно в share sheet, и повторные нажатия за день переписывают один файл вместо того,
чтобы копить в кеше почти одинаковые копии.

**Готово, когда:** «Экспорт» пишет файл через `new File(Paths.cache, ...)` и
открывает системный share sheet; «Импорт» выбирает файл, показывает предупреждение о
полной замене данных и восстанавливает привычки с историей; битый или обрезанный
файл не оставляет базу в промежуточном состоянии (проверяю намеренно испорченным
JSON), а файл с чужой версией отклоняется с сообщением, а не импортируется наполовину;
после импорта перезагружены оба стора — отметки на «Сегодня» те, что в файле, а не
дозагруженные, — уведомления перепланированы, стрики совпадают с исходным
устройством; отмена в пикере и отказ share sheet ничего не ломают.

Коммит: `feat: json export and import`.

### Этап 10 — Полировка

Файлы: `db/provider.tsx`, `app.json`, `assets/images/*`, `(tabs)/index.tsx`,
`(tabs)/settings.tsx`, `components/habit/habit-form.tsx`, `color-picker.tsx`,
`time-picker-field.tsx`. Eslint настраивать не нужно: `eslint.config.js` уже лежит в
корне и `npm run lint` проходит.

**Два error boundary, а не один.** Внешний обёрнут вокруг `SQLiteProvider` и ловит
падение миграции — то самое, ради которого этап и заводился. Внутренний стоит уже под
провайдером, вокруг детей: экраны обязаны жить внутри провайдера (им нужен
`useSQLiteContext`), поэтому падение любого из них дошло бы до внешнего boundary и было
бы показано как «не удалось открыть базу данных». Внутренний забирает эти случаи себе и
оставляет внешнему единственное, что тот действительно видит — открытие базы.

**Экран ошибки сам прячет splash.** `SplashScreen.hideAsync()` вызывается в `RootStack`,
а он при падении не монтируется вообще: сообщение осталось бы навсегда под сплэшем, то
есть ровно тем непроходимым экраном, который boundary и должен был заменить. Поэтому
`hideAsync` продублирован в самом экране ошибки.

**Пустые состояния — на каждом экране.** «Сегодня» различает «привычек пока нет» и «на
этот день ничего не запланировано» и показывает их **только после загрузки стора**:
на холодном старте стор пуст один кадр, и негейтированное состояние встречало бы каждый
запуск словами «привычек пока нет». «Статистика» так же ждёт свой список,
`habit/[id]` — свою одноразовую догрузку (этап 8), `+not-found` даёт кнопку на главную.
В настройках пустое состояние живёт в `ListEmptyComponent`, и контейнеру списка нужен
`flexGrow: 1`: `flex: 1` внутри `contentContainer` схлопывается в нулевую высоту, и
сообщение просто не видно.

**Экран «не удалось открыть базу» умеет из себя выйти.** Совет перезапустить приложение
сам по себе бесполезен: файл, который не открылся, останется на месте и на следующем
запуске, а до импорта в настройках уже не добраться — экранов под провайдером нет. Поэтому
у внешнего boundary есть действие «Сбросить базу данных»: `Alert` с подтверждением и
удаление файла. Именно удаление, а не починка: у файла, который SQLite отказывается
открыть, читать нечего.

Удаляются `habits.db` и его спутники `-wal` / `-shm` напрямую через `File.delete()`, а не
через `deleteDatabaseAsync`: тот отказывает с «Unable to delete database that is currently
open». `SQLiteProvider` открывает файл успешно и падает уже на первом запросе внутри
`migrate`, то есть соединение живо, а ручки на него снаружи нет; нативные соединения
считаются по ссылкам, так что и переоткрытие ради закрытия его не освободит. По той же
причине экран не возвращает управление в повтор — нативный кеш отдал бы то же самое
сломанное соединение, — а просит перезапустить приложение: следующий запуск создаёт базу
с нуля, и в настройках можно импортировать бэкап.

**У модалок есть явная кнопка закрытия.** `presentation: 'modal'` закрывается свайпом
вниз, но об этом жесте на экране ничего не сообщает, а VoiceOver его вовсе не выполнит.
Оба роута `habit/*` получают её через `headerRight` — справа, где iOS держит закрытие
шита, — и глифом `xmark`, а не словом: это одна и та же кнопка на обеих модалках, и она
занимает куда меньше шапки, чем подпись «Отмена».

**Выключенный контрол гасится прозрачностью, а не только заливкой.** `colors.disabled`
темнее `surfaceAlt` в светлой теме, поэтому выключенная стрелка в настройках выходила
заметнее активной кнопки рядом. `opacity.disabled` опускает композит ниже `surfaceAlt` в
обеих темах и заодно приглушает глиф.

**Роли доступности — только те, что понимает iOS.** `accessibilityRole="radio"` и
`"checkbox"` в UIKit не отображаются ни в какой trait: свотчи цвета, дни недели, эмодзи,
чипы «Статистики» и переключатель «Архивные» экспортировались как безымянные элементы —
VoiceOver не называл их контролами и не читал выбранность. Везде `role="button"` и
`accessibilityState={{ selected }}`. `Switch` напоминания получил свой
`accessibilityLabel`: соседний `Text` VoiceOver с ним не связывает.

**Тач-таргеты.** Размером в 44pt: `Button`, `IconButton`, `CheckButton`, клетки полоски
дат, дни недели, эмодзи (6 колонок дают ~50pt), чипы и переключатель на «Статистике»,
строка и кнопка меню в настройках. Через `hitSlop` — два места, где элемент физически
меньше: свотчи цвета (восемь в ряд, ~36–38pt) и ссылка «Настройки» под переключателем
напоминания. У свотчей слоп берёт ровно половину 8pt зазора с каждой стороны, так что
до 44pt добирает, а области соседей не перекрывает.

**Шрифт в поле ввода.** `TextInput` в форме — единственный текст, который рисуется не
через `components/ui/text.tsx`, поэтому `allowFontScaling: false`, семейство и размер
ему проставлены вручную из токенов. Без этого одно поле росло бы с системным Dynamic
Type посреди фиксированной вёрстки и рисовалось бы системным шрифтом вместо
`ui-rounded`. `lineHeight` из токена не берётся: на iOS он подрезает текст внутри
`TextInput`.

**Отказы промисов не остаются без обработки.** Архивация с карточки на «Сегодня» и все
мутации в настройках (`runMutation`) гасят отказ логом: unhandled rejection всплыл бы
warning'ом в Metro ради ошибки, которую пользователь всё равно только повторит.

**Иконка, splash, bundle id.** `icon.png` 1024×1024 без альфы и `splash-icon.png` —
свои, под палитру; фон splash — акцент `#6C4DFF`, в тёмной теме `#241E3A` (accentSoft),
вместо дефолтного эксповского `#208AEF`. Шаблонный Icon Composer-бандл
(`assets/expo.icon`) удалён. `ios.bundleIdentifier` — `com.mar1798.habbits-line`.
Отображаемое имя под иконкой — «Habbits Line» (`name` в `app.json`); `slug`, `scheme` и
bundle id остались прежними, чтобы не порвать ни ссылки, ни установленную сборку.
Имя попадает в нативный проект только через `prebuild`, поэтому после его смены нужен
`npx expo prebuild --platform ios`. В первый раз этого не сделали, и сборка ещё какое-то
время выходила с именем `habbits-line` (слаг) под иконкой при правильном `app.json` —
см. риск про `prebuild` в разделе 6.

**Готово, когда:** нет ни одного экрана без осмысленного пустого состояния, ни
одного тач-таргета меньше 44pt, обе темы выглядят законченно, splash и иконка — свои,
падение миграции показывает сообщение, а не белый экран и не вечный splash,
`npx tsc --noEmit` чисто, `npx jest` зелёный, `npx expo export --platform ios` и Metro
без warning.

Коммит: `chore: v1 polish`.

### Этап 11 — Два языка: русский и английский

**Новых зависимостей нет.** Дефолт — русский, и он не зависит от языка системы, поэтому
`expo-localization` не нужен: единственное, ради чего его ставили бы, — режим
«Системный», а его здесь нет (см. ниже). Локали дат берутся из уже стоящего `date-fns`.

Файлы: `i18n/index.ts`, `i18n/ru.ts`, `i18n/en.ts`, `i18n/plural.ts`,
`hooks/use-i18n.ts`, `store/settings-store.ts`, `(tabs)/settings.tsx`,
`lib/notifications.ts`, `lib/backup.ts` и все экраны и компоненты, где лежали строки:
`app/_layout.tsx`, `app/+not-found.tsx`, `(tabs)/_layout.tsx | index.tsx | stats.tsx`,
`app/habit/new.tsx | [id].tsx`, `components/habit/*`, `components/stats/*`,
`db/provider.tsx`.

**Миграции нет.** Язык — строка в `app_settings` под ключом `language`. Таблица заведена
на этапе 2 ровно под такие настройки, схема не меняется. Стор настроек
(`store/settings-store.ts`) получил поле `language` рядом с `themeMode` и читает обе
строки одним `load()` при старте.

**Два значения, а не три: `'ru' | 'en'`, по умолчанию `'ru'`.** Русский — язык этого
приложения по умолчанию, английский — осознанное переключение в настройках. Режим
«Системный» не заводим: приложение личное, его первый язык русский, и третье состояние
добавляло бы ветку в расчётах и в тестах ради пользователя, которого у него нет. Любое
другое значение в строке (сборка постарше, правка файла руками) откатывается на `'ru'` —
тем же разбором, что и остальные настройки. Оборотная сторона решения: англоязычный
пользователь встречает первый запуск на русском и ищет переключатель по позиции, поэтому
подписи переключателя — эндонимы («Русский» / «English»), одинаковые в обоих словарях: их
читают именно тогда, когда текущий язык прочесть не могут.

**Словарь — типизированный объект, а не формат переводов.** `ru.ts` объявлен `as const` и
является источником ключей, `en.ts` — `Record<keyof typeof ru, string>`: забытый перевод
падает на `npx tsc --noEmit`, а не показывается пустой строкой. Библиотеку перевода не
берём: ~150 строк не окупают чужой рантайм и формат, а полноту словаря они проверяют
только в тестах, тогда как типы — на компиляции. Подстановки — свои, по `{name}`:
`translate()` заменяет плейсхолдеры, а неизвестный оставляет как есть — в UI он виден как
`{name}`, что для незаполненного параметра и правильно.

**Плюрализация — два правила в одном файле, но не одна функция.** Правило
«1 день / 2–4 дня / 5 дней» жило двумя копиями (`streak-card.tsx`, `habit-card.tsx`);
обе уехали в `i18n/plural.ts`. Там `russianPlural(n, {one, few, many})` и
`englishPlural(n, {one, other})`: у английского форм две, и общая сигнатура заставляла бы
каждый английский вызов нести форму, которой у языка нет. Выбор между ними — один
`pluralize(language, key, n)` в `i18n/index.ts`, так что вызывающий код о разнице не
знает. Формы лежат в словарях (`ruPlurals` / `enPlurals`), склеиваются с фразой через
плейсхолдер: `'Цель: {count} {times} в день'`.

**Даты форматируются локалью, но считаются по-прежнему от понедельника.** `date-fns`
получает `ru` или `enUS` тем же глубоким импортом (`date-fns/locale/en-US`), чтобы в бандл
не приехал барель всех локалей; оба импорта собраны в `i18n/index.ts`, а компоненты берут
локаль из хука. Локаль отдаётся **только** в `format`: `startOfWeek` и вся арифметика
`lib/date.ts` остаются без неё. У `enUS` неделя начинается с воскресенья, и локаль,
попавшая в арифметику, сдвинула бы и полоску дат, и сетку хитмапа, и смысл
`schedule_mask`, где бит 0 — понедельник. Подписи дней недели берутся из словаря
(`ruWeekdays` / `enWeekdays`, тип `WeekdayLabels`), а не из date-fns: там нужны
двухбуквенные метки и однобуквенные инициалы в порядке маски.

**Смена языка перепланирует уведомления.** Тело напоминания вшивается в триггер в момент
планирования, поэтому уже запланированные уведомления остались бы на прежнем языке до
следующей правки привычки. `setLanguage` вызывает тот же полный пересчёт под мьютексом,
что и мутации привычек; его падение логируется, а не пробрасывается — язык-то сменился.

**Строки вне React берут язык из стора напрямую.** `lib/notifications.ts` не находится в
дереве компонентов и читает `useSettingsStore.getState().language` в `buildContent`, а не
хук. Экраны и компоненты идут через `hooks/use-i18n.ts` — переключение перерисовывает UI
без перезапуска. Хук отдаёт по одному замороженному набору на язык из модульного кэша:
`t` и `locale` попадают в списки зависимостей (чипы статистики, сетка хитмапа), и новое
замыкание на каждый рендер пересобирало бы их каждый раз.

**Ошибки импорта бросаются кодом, а не текстом.** `lib/backup.ts` клал русскую фразу в
`Error.message`, и её показывал `Alert` в настройках. Оставить так — значит получить
единственное место, куда язык не доедет, и заметить это только на чужом устройстве.
Теперь модуль бросает `BackupError` со стабильным кодом (`unsupported_version`,
`malformed_file`, `unrecognized_format`, `orphan_entries`, `sharing_unavailable`) и
параметрами для плейсхолдеров, а текст подбирается на месте показа. Языка сам модуль не
знает вовсе — стор ему не нужен.

**Экраны фатальной ошибки — единственное место, где язык всегда дефолтный.**
`db/provider.tsx` показывает их, когда база не открылась, то есть строку `language`
прочитать было неоткуда. Они рендерятся на русском. Это дефолт, так что ничего не
потеряно — но если дефолт когда-нибудь перестанет быть русским, это первое место, которое
это заметит.

**Что не переводится:** названия и эмодзи привычек (это пользовательские данные), имя
приложения под иконкой (потребовало бы локализованных `InfoPlist` и ещё одного
`prebuild` — в скоуп не входит) и содержимое файла бэкапа. Язык лежит в `app_settings`, а
экспорт несёт только `habits` и `entries`, поэтому импорт чужого файла язык не меняет.

Тесты: `i18n/__tests__/plural.test.ts` — русские границы (0, 1, 2, 4, 5, 11, 12, 14, 21,
22, 101, 111) и английская пара; плюс три проверки словарей, которых типы не дают:
непустые строки, одинаковые наборы плейсхолдеров в обоих языках и семь подписей дней в
каждом.

**Готово:** в настройках есть переключатель «Русский / English», тап по нему меняет язык
всего UI без перезапуска, и выбор переживает перезапуск приложения; названия месяцев над
полоской дат и в хитмапе, дни недели и множественные числа («5 дней» / «5 days»,
«3 раза» / «3 times») верны в обоих языках; неделя в обоих языках начинается с
понедельника, а расписание привычки после переключения языка не съезжает; сообщения об
ошибках экспорта и импорта переведены; смена языка перепланирует напоминания, так что
следующее приходит на новом языке; кириллицы в коде не осталось нигде, кроме `i18n/ru.ts`,
комментариев и одного примера в `i18n/__tests__/plural.test.ts`; `npx tsc --noEmit` чисто,
`npx jest` зелёный, `npx expo export --platform ios` и Metro без warning.

Коммит: `feat: russian and english localization`.

### Этап 12 — Траты: бюджет периода, категории, экран и блок в статистике

Этап большой, поэтому разбит на три подэтапа: **12.1 — данные**, **12.2 — экран
и модалки**, **12.3 — настройки и статистика**; все три сделаны. Каждый подэтап — отдельная сессия и
отдельный коммит, порядок строгий: 12.2 опирается на репозитории и сторы из 12.1,
12.3 — на роуты форм из 12.2. Общие решения собраны здесь, частности — в блоке своего
подэтапа.

**Новых зависимостей нет.** Всё берётся из уже стоящего: `expo-sqlite`, `zustand`,

нужен: модалки — обычные роуты `expo-router`, как у привычек.

#### Что осознанно не делаем (во всех трёх подэтапах)

Валюту и её символ; доходы и пополнения (баланс — это бюджет, а не кошелёк); копейки;
время траты и комментарий (в статистике «почему» — это название категории); повторяющиеся
и плановые траты; перенос остатка в следующий период; лимиты по отдельным категориям;
уведомления о перерасходе; перетаскивание порядка категорий; траты в экспорте и импорте —
они вынесены в этап 13.

### Этап 12.1 — Данные трат: схема, период, суммы, сторы

Подэтап без единого пикселя UI: схема, репозитории, чистая логика и сторы под неё.
Так весь расчётный слой закрывается тестами до того, как на него сядет экран, и правка
арифметики периода в 12.2 не тянет за собой правку вёрстки.

Файлы: `db/migrations.ts`, `db/types.ts`, `db/expense-categories-repo.ts`,
`db/expenses-repo.ts`, `db/budgets-repo.ts`, `store/expense-categories-store.ts`,
`store/expenses-store.ts`, `store/settings-store.ts`, `lib/period.ts`, `lib/money.ts`,
`lib/expenses.ts`, `constants/design-tokens.ts`, `constants/emoji.ts`,
`lib/__tests__/period.test.ts`, `money.test.ts`, `expenses.test.ts`.

#### Схема: миграция v1 → v2

Старый блок v0→v1 не редактировался, `DATABASE_VERSION` стал `2`, добавлен новый блок.
Прагма `foreign_keys = ON` уже стояла в начале `migrate(db)`, до проверки версии, — новые
внешние ключи работают с первого же открытия. Три таблицы (`expense_categories`,
`expenses`, `expense_budgets`), их индексы и обоснования переехали в раздел 2; здесь
осталось только то, что к схеме не сводится.

День начала периода — строка в `app_settings` под ключом `expense_period_start_day`
(`'1'`..`'28'`, дефолт `'1'`). Схема под это не менялась: таблица на этапе 2 заведена
ровно для таких настроек.

Сидируемые эмодзи обязаны присутствовать в `constants/emoji.ts` — иначе форма правки
категории не сможет показать выбранное значение. Шесть недостающих (`💊 🏠 🎬 🛍️ 🚌 📦`)
добавлены в набор этим подэтапом; набор один на оба пикера, потому что `emoji-picker.tsx`
общий для формы привычки и формы категории.

#### Период с произвольного дня

`lib/period.ts` — единственное место арифметики периодов, как `lib/schedule.ts` для
дней недели:

```
periodStartFor(dateKey, startDay) -> dateKey   // начало периода, в который попадает дата
periodEndFor(dateKey, startDay)   -> dateKey   // последний день периода (включительно)
periodLength(periodStart, startDay) -> number  // дней в периоде
shiftPeriod(periodStart, delta)   -> dateKey   // предыдущий/следующий период
```

**День старта ограничен 1..28.** 29–31 не существуют в каждом месяце, и любой выбор
из них требует правила подтягивания к последнему дню, которое ломает равенство
«начало следующего периода = конец текущего + 1 день». Ограничение снимает целый
класс краевых случаев ценой одного дня в году для тех, у кого зарплата 29-го.

**Ключ периода — дата его первого дня, а не `'YYYY-MM'`.** При старте 6-го числа
период с 6 августа по 5 сентября не является ни августом, ни сентябрём; дата начала
однозначна при любом дне старта. Подпись такого периода — «6 авг — 5 сен».

**День старта не версионируется**, как расписание и цель привычки. Меняю его — границы
пересчитываются для всей истории, и строки `expense_budgets` со старыми границами
перестают совпадать с началом какого-либо периода. Они не удаляются и не показываются,
но и не теряются: их подхватывает наследование (ниже), потому что оно ищет последнюю
строку **до** начала периода, а не точное совпадение.

#### Бюджет: своя строка на период, наследование назад

`resolveBudget(budgets, periodStart)`: точная строка по ключу; если её нет — последняя
строка с `period_start < periodStart`; если и такой нет — бюджета нет. Правка бюджета
всегда пишет строку **ровно на текущий период**.

Правило живёт **чистой функцией в `lib/expenses.ts`, а не двумя запросами в репозитории**:
подэтап требует теста на наследование, а тестируется только чистая логика.
`budgets-repo.getBudgetFor` читает таблицу целиком (`listBudgets`) и отдаёт её в
`resolveBudget` — строк там столько, скольким периодам бюджет задавали руками, то есть
единицы, и это дешевле сэкономленного круга по SQL. Определение правила при этом ровно
одно.

Так уживаются «бюджет свой на каждый период» и «новый период наследует прошлый», не
заводя фонового задания, которое создавало бы строку на границе периода: приложение
офлайновое, его могут не открывать месяцами, и такому заданию просто негде исполниться.
Наследование действует только назад по времени: у периодов **раньше** первого
заданного бюджета его нет — и это верно, тогда его действительно не задавали.

Состояние «бюджета нет» — законное и для расчёта: `lib/expenses.ts` возвращает доли
категорий и без знаменателя, не деля на ноль. Как это показано на экране — в 12.2.

#### Палитра трат — 16 цветов

Отдельный набор в `design-tokens.ts`: тип `ExpenseColorKey`, объект `expenseColors`,
`DEFAULT_EXPENSE_COLOR`, `resolveExpenseColorKey`, `resolveExpenseColor` — зеркало
API палитры привычек. Восемь ключей повторяют hex палитры привычек
(`violet`, `indigo`, `sky`, `teal`, `green`, `amber`, `coral`, `pink`), восемь новых —
промежуточные тона: `plum`, `blue`, `mint`, `olive`, `orange`, `rose`, `brown`, `slate`.

**Почему отдельный тип, а не расширение палитры привычек.** Требования к цветам разные:
цвет привычки — фон под подписью `N/M`, цвет категории — заливка сегмента полосы и
плитки. Общий тип означал бы, что 16 цветов немедленно приезжают и в пикер привычки,
где восьми хватает, а шкала из шестнадцати перестаёт читаться как шкала. Совпадение
hex у восьми ключей — сознательное: семья тонов одна на всё приложение.

Новые восемь подбираются по действующему правилу палитры: **выравнивание по контрасту,
а не по светлоте**, светлые варианты ~4.85:1 против `onAccent` (в модалке траты
выбранная плитка красится цветом категории, а её название пишется поверх), тёмные —
не ниже 6.5:1 на `bg`. Неизвестный ключ откатывается на `violet` — единственная точка
проверки `resolveExpenseColorKey`, через неё же нормализуется значение при открытии
формы категории, чтобы сохранение переписывало чужой ключ, а не возвращало его в базу.

Уникальность цвета не навязывается: 16 цветов на 8 сидированных категорий оставляют
запас, но две категории одного цвета — законное состояние (пикер помечает занятые,
не блокируя их). Запрет означал бы, что после 16 категорий новую завести нельзя.

#### Суммы

Целые числа, `INTEGER`, без копеек и без символа валюты — «просто цифра».

`lib/money.ts` — `formatAmount(n)`: группировка разрядов узким неразрывным пробелом
(U+202F), минус для отрицательного остатка. Своя функция, а не `Intl.NumberFormat`:
валюты нет, локализовать нечего, а поведение ICU на Hermes зависит от сборки и его
пришлось бы проверять отдельно. Функция чистая и покрыта тестами.

#### Сторы

**Стор читает период целиком, а день выводится из него.** `expenses-store` держит траты
одного периода (`listExpensesBetween(from, to)`), его границы и бюджет; список дня —
чистая деривация фильтром. Полосе и остатку всё равно нужен весь период, а переключение
дня после загрузки становится бесплатным и не мигает данными предыдущего дня. Перезагрузка
происходит только когда выбранная дата ушла в другой период. То же рассуждение, что у
`listAllEntries` на этапе 6, применённое к одному периоду вместо всей таблицы.

Мутации — оптимистичные, как `cycle` в `entries-store`: стор патчит массив синхронно,
ждёт репозиторий и откатывает при ошибке. Haptics на сохранении траты — `success`, на
удалении — `warning`, через существующий `lib/haptics.ts`.

`settings-store` получает день начала периода: чтение при старте и запись через
`settings-repo`, ровно как язык и тема на этапах 8 и 11.

**Сторы пишутся здесь, хотя их потребитель появится в 12.2.** Их форма продиктована
не вёрсткой, а тем, как читаются данные (период целиком, оптимистичный патч), — это
часть слоя данных. Разрезать иначе значило бы в 12.2 писать и стор, и экран разом, а
проверять только глазами.

#### Бюджет не задан и перерасход

**Состояние «бюджет не задан»** (свежая установка, или улистал в самое начало истории):
вместо остатка — надпись «Бюджет не задан» и кнопка «Задать»; полоса при этом
показывает 100% ширины, разбитой на доли категорий, — она остаётся осмысленной без
знаменателя. Траты пишутся и без бюджета.

**Перерасход.** Полоса зажата в 100% (сегменты категорий нормируются к сумме трат),
число остатка становится отрицательным и красится токеном `danger`, подпись — «Перерасход».
Причина зажима: полоса, вылезающая за трек, ломает вёрстку карточки, а сам факт
перерасхода уже сказан числом и цветом.

совместимость со своей ценой. Здесь версия формата поднимается до 2, и файл начинает
нести `expense_categories`, `expenses` и `expense_budgets` рядом с `habits` и `entries`.

- Файл **v1 импортируется** как раньше: траты в нём просто отсутствуют, существующие
  категории и траты при этом не трогаются — импорт v1 заменяет только привычки.
- Файл **v2 на старой сборке** отвергается существующей ошибкой `unsupported_version` —
  проверка версии для этого и написана.
- Осиротевшие траты (`category_id`, которого нет в файле) — та же ошибка класса
  `orphan_entries`, что и для записей без привычки: файл битый, импортировать его
  частично опаснее, чем отказаться.
- `expense_period_start_day` живёт в `app_settings` и в бэкап **не едет**, как тема и
  язык: экспорт несёт данные, а не настройки устройства.

**Готово, когда:** экспорт даёт файл версии 2 с тратами, категориями и бюджетами;
импорт этого файла на чистой установке восстанавливает экран трат целиком, включая
цвета категорий и бюджеты периодов; импорт старого файла v1 проходит и не удаляет
существующие траты; битый файл даёт переведённое сообщение об ошибке.

Коммит: `feat: expenses in backup export and import`.

## 6. Риски

**Стрики и часовые пояса.** Дата всегда `'YYYY-MM-DD'` из локального времени, все
преобразования — только через `lib/date.ts`. `toISOString()` запрещён **для ключей
дат** (он даёт UTC и на восточных таймзонах после полуночи отдаёт вчерашний день);
для `created_at` / `updated_at` ISO-таймстемп наоборот и нужен. Перелёт в другую
таймзону не переписывает прошлые записи — они уже строки.

**Переход через полночь.** Приложение, оставленное открытым на ночь, покажет
вчерашний день как «сегодня». Лечение: пересчёт текущей даты по `AppState` →
`active` и по таймеру до ближайшей полуночи — один общий хук
`hooks/use-today-key.ts` на все экраны, у которых есть понятие «сегодня»
(«Сегодня» — полоска дат, «Статистика» — граница стрика и последняя клетка хитмапа).
Осознанно НЕ делаем настраиваемый «день до 4 утра» в v1: это заражает все расчёты
вторым понятием даты.

**Правка расписания задним числом.** Схема и цель не версионируются, поэтому
изменение привычки переписывает её прошлую статистику. Принято осознанно (см.
базовые решения); в UI редактирования — короткая подпись, что смена расписания
влияет на историю.

**`PRAGMA foreign_keys` и каскад.** Прагма уровня соединения, а не файла. Живёт в
начале `migrate()`, до проверки `user_version`, и проверяется в критерии этапа 2 —
иначе каскадное удаление отвалится молча со второго запуска.

**Перепланирование уведомлений при смене расписания.** Инкрементальная правка —
источник рассинхрона. Стратегия: любое изменение привычки (время, дни, архивация,
удаление, импорт) вызывает полный пересчёт —
`cancelAllScheduledNotificationsAsync()`, затем планирование заново по всем активным
привычкам, под мьютексом. Все уведомления в приложении наши, так что «отменить всё»
безопасно.

**Лимит iOS (64 запланированных уведомления).** Repeating-триггеры считаются каждый
отдельно, поэтому привычка с 7 днями = 7 записей → всего ~9 привычек с
напоминаниями. Смягчение: если выбраны все 7 дней — один `DAILY`-триггер вместо семи
`CALENDAR`; иначе по одному `CALENDAR` (`weekday` + `repeats`) на день. Плюс счётчик в `lib/notifications.ts`:
на `NOTIFICATION_WARNING_THRESHOLD` (55 запланированных) показываем понятное
предупреждение в настройках, а не молча теряем напоминания.

**Weekday-нумерация — три разные системы.** У нас бит 0 = понедельник, у
`date-fns` `getDay()` 0 = воскресенье, у `CalendarTriggerInput` (как и у
`WeeklyTriggerInput`) `weekday: 1` = воскресенье. Обе конвертации живут ровно в одном месте (`lib/schedule.ts`) и
покрыты тестами на этапе 6.

**Expo Go против dev build.** Локальные уведомления в Expo Go работают (недоступны
там только push-уведомления), поэтому этапы 1–9 проходимы в Expo Go. Но поведение
splash при запуске из уведомления в Expo Go отличается — финальную проверку этапа 7
делаем на dev build.

**`ios/` не пересобирается сам.** Папка сгенерированная и лежит в `.gitignore`, но
собирается-то из неё. Всё, что приходит из `app.json` — отображаемое имя, иконка, splash,
bundle id — попадает в сборку только через `npx expo prebuild --platform ios`. Один раз
это уже стоило релизу неправильного имени под иконкой: `app.json` был верный, а `ios/`
остался от сборки до переименования. Правило: тронул `app.json` — прогони `prebuild` и
проверь `ios/habbitsline/Info.plist`, а не только `expo config`.

**Недоверенные данные из импорта.** Файл бэкапа — единственный вход, через который в базу
попадает то, чего UI создать не может. Схема проверяет типы, но не значения, поэтому
проверки живут в `lib/backup.ts` (см. раздел «Формат» этапа 9), а расчёты держат
дополнительный запас прочности: `forEachDateKey` на невалидном ключе ничего не обходит и
отдаёт пустой стрик вместо `RangeError` из рендера, а `scheduleForHabit` пропускает одну
привычку с битым `reminder_time`, а не роняет пересчёт для всех остальных.

**Стоимость расчёта стриков.** `computeStreaks` идёт по дням от самой ранней записи до
сегодня, то есть линейно по всей истории привычки, и делает это на каждый пересчёт
«Статистики». С `parse`/`format` из date-fns на каждой итерации это 35 мс на трёх годах и
59 мс на десяти (desktop Node; на устройстве в 3–5 раз больше). Поэтому обход вынесен в
`forEachDateKey`, который ведёт один мутируемый `Date` и собирает ключ вручную: те же
данные считаются за 2 и 7 мс. Если история когда-нибудь начнёт измеряться десятилетиями,
следующий шаг — считать `best` инкрементально в базе, а не заново из `entries`.

**Язык и уже запланированные уведомления.** Текст напоминания попадает в систему в
момент планирования, а не показа, поэтому смена языка без пересчёта оставляла бы
напоминания на прежнем языке до следующей правки привычки. Смена языка — такая же
мутация с полным пересчётом, как правка расписания. Оборотная сторона общая с этапом 7:
без разрешения на уведомления пересчёт пропускается, и язык применяется только к UI —
уведомлений всё равно нет.

**Миграции БД на уже установленном приложении.** Соблазн «поправить первую миграцию»
велик и смертелен: у установленной копии `user_version` уже 1, и правка просто не
применится. Правило: только новые блоки. Перед каждой миграцией на реальном
устройстве — экспорт JSON (этап 9 существует в том числе для этого).

## 7. Где скиллы и документация повлияли на архитектуру

- **expo-sqlite (docs + исходники).** `SQLiteProvider` + `useSuspense` вместо
  самописного синглтона; миграции через `PRAGMA user_version` в `onInit`; WAL включаем
  при создании базы, `foreign_keys` — при каждом открытии; импорт идёт через
  `withExclusiveTransactionAsync`, потому что обычная транзакция захватывает
  посторонние параллельные запросы. Оттуда же — что эксклюзивная транзакция открывает
  **новое соединение** (`useNewConnection: true`), где `foreign_keys` не включён:
  импорт поэтому не полагается на каскад и проверяет ссылки сам (этап 9).
- **expo-notifications (docs).** Локальные уведомления доступны в Expo Go;
  `weekday` в `CalendarTriggerInput` / `WeeklyTriggerInput` — 1..7 с воскресеньем
  первым (отсюда разделение `DAILY` / `CALENDAR` ради лимита iOS); для показа при
  открытом приложении нужен `setNotificationHandler`, для холодного старта по тапу —
  `getLastNotificationResponse()` с последующим `clearLastNotificationResponse()`,
  иначе ответ живёт дальше и срабатывает на каждом запуске; на iOS смотрим
  `ios.status`, а не корневой `status`.
- **@expo/ui (docs).** Пакет уже в проекте и даёт нативный `DatePicker` — новая
  зависимость на выбор времени не нужна.
- **expo-file-system (docs).** Экспорт на новом объектном API (`File`, `Paths`), а не
  на устаревшем `readAsStringAsync`.
- **react-native-best-practices.** Списки только `FlatList` (никаких `ScrollView` +
  `.map`); анимации только `transform` / `opacity` на UI-потоке Reanimated (полоса
  прогресса — единственное задокументированное исключение); zustand с атомарными
  селекторами, чтобы отметка одной привычки не перерисовывала весь список; в проекте
  включён `reactCompiler: true`, поэтому ручные `useMemo` / `useCallback` не
  добавляем без замеренной проблемы; тяжёлые расчёты (стрики, хитмап) вынесены из
  рендера в чистые функции `lib/streaks.ts` — SQL-агрегатами их не считают, потому что
  правила «день закрыт» и «день вне расписания» живут в одном месте с тестами, а цена
  обхода снята в `forEachDateKey` (см. риск про стоимость расчёта стриков).
